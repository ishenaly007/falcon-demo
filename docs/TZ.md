# Техническое задание и план реализации

**Проект:** WorkTime — учёт рабочего времени сотрудников
**Основание:** тестовое задание Falcon AI на позицию «Программист»
**Версия документа:** 1.0
**Статус:** реализовано (см. раздел 11 «Критерии приёмки»)

---

## 1. Цель

Сделать с нуля небольшое веб-приложение для учёта рабочего времени сотрудников. Пользователь добавляет сотрудников, запускает и останавливает таймер с описанием задачи и смотрит записи и итоги за выбранный период. Данные не должны теряться при перезапуске.

Вторая цель — показать **осмысленную работу с ИИ**: постановку задач нейросети, проверку сгенерированного кода, поиск и исправление ошибок.

## 4. Функциональные требования

### FR-1. Сотрудники
- FR-1.1. Создание: имя (обязательно, 1–100 символов, пробелы по краям обрезаются), должность (необязательно, до 100 символов; пустая строка сохраняется как «нет»).
- FR-1.2. Список сотрудников по алфавиту; у каждого виден идущий таймер, если он есть.
- FR-1.3. Ошибки валидации — `400` с понятным текстом на русском.

### FR-2. Таймер
- FR-2.1. Старт: обязательное описание задачи (1–500 символов). Создаётся запись с `started_at = сейчас`, `ended_at = NULL`.
- FR-2.2. Стоп: идущей записи проставляется `ended_at = сейчас`, а в ответе возвращается длительность.
- FR-2.3. **Повторный старт при идущем таймере → `409 Conflict`.** Идущий таймер не меняется: та же задача, то же время старта.
- FR-2.4. Стоп без идущего таймера → `409`.
- FR-2.5. Таймеры разных сотрудников независимы.
- FR-2.6. Несуществующий сотрудник → `404`.

### FR-3. Отчёт
- FR-3.1. Период задаётся датами `from..to` включительно, в часовом поясе пользователя (параметр `tz`, по умолчанию — пояс из настроек).
- FR-3.2. Сводка: общее время, число записей и для **каждого** сотрудника — его время, число записей и признак «сейчас работает».
- FR-3.3. Список записей за период, новые сверху, с фильтром по сотруднику.
- FR-3.4. В итог засчитывается только часть записи, попадающая в период. Запись 23:00–01:00 даёт по часу в каждый из двух дней.
- FR-3.5. Идущий таймер учитывается до текущего момента.
- FR-3.6. **Пустой отчёт — штатная ситуация:** `200`, итог 0, у каждого сотрудника 0, флаг `empty = true`. В интерфейсе — понятная заглушка.
- FR-3.7. Некорректный период (`from > to`, длиннее 366 дней, битая дата, неизвестный пояс) → `400`.

### FR-4. Интерфейс
- FR-4.1. Одна страница: слева «Команда» (добавление, карточки с таймерами), справа «Отчёт».
- FR-4.2. Живые счётчики `ЧЧ:ММ:СС` у идущих таймеров; итоги отчёта тоже растут в реальном времени.
- FR-4.2a. Список записей отчёта — постранично, по 10 записей; при смене периода или сотрудника — снова первая страница.
- FR-4.3. Пресеты периода: «Сегодня», «Неделя» (пн–вс), «Месяц» и произвольный период.
- FR-4.4. Уведомления об успехе и ошибках; ошибки сервера показываются текстом из поля `detail`.
- FR-4.5. Адаптивность от 375px, светлая и тёмная темы.

## 6. Модель данных

```
employee                         time_entry
─────────────────────────        ──────────────────────────────────────────
id           BIGINT PK           id                   BIGINT PK
name         VARCHAR(100) NN     employee_id          BIGINT FK → employee
position     VARCHAR(100)        description          VARCHAR(500) NN
created_at   TIMESTAMPTZ NN      started_at           TIMESTAMPTZ NN
                                 ended_at             TIMESTAMPTZ      ← NULL = таймер идёт
                                 running_employee_id  BIGINT GENERATED  ← UNIQUE
```

**Как работает ограничение «один идущий таймер».** Колонка `running_employee_id` вычисляется как `CASE WHEN ended_at IS NULL THEN employee_id END`. Уникальный индекс пропускает сколько угодно `NULL` (остановленные записи), но не два одинаковых `employee_id` (два идущих таймера). Аналог в PostgreSQL — частичный индекс `UNIQUE (employee_id) WHERE ended_at IS NULL`.

Индексы: `(employee_id, started_at)` для записей сотрудника и `(started_at)` для отчётов за период.

## 8. Ключевые алгоритмы

**Период → моменты времени.** `from`, `to` и пояс превращаются в полуинтервал `[from 00:00, (to + 1 день) 00:00)`. Полуинтервал исключает двойной счёт на стыке соседних периодов.

**Выборка.** Берутся записи, пересекающиеся с периодом: `started_at < end AND (ended_at IS NULL OR ended_at > start)`.

**Обрезка.** Для каждой записи считается
`overlap = max(0, min(конец записи, конец периода) − max(начало записи, начало периода))`,
где для идущего таймера «конец записи» — это текущий момент. Это отдельная чистая функция `TimeMath.overlapSeconds`, у неё свои юнит-тесты на 8 граничных случаев.

**Конкурентный старт.** `SELECT … FOR UPDATE` по строке сотрудника → проверка, нет ли идущей записи → вставка + `flush`. Если гонка всё же прорвётся, сработает уникальный индекс, а исключение превратится в `409`.

## 12. Риски и решения

| Риск | Решение |
|---|---|
| Два одновременных «старта» создают два таймера | Блокировка строки + уникальный индекс + многопоточный тест |
| Записи на границе суток считаются дважды или теряются | Полуинтервалы и обрезка по периоду + тест на запись через полночь |
| «Сегодня» у пользователя и на сервере — разные дни | Браузер передаёт свой пояс (`tz`), сервер строит период в нём |
| Тесты зависят от реального времени и «мигают» | `Clock` как бин, в тестах — управляемые часы |
| Тест сохранности случайно пишет в рабочую БД | Найдено и исправлено: URL БД передаётся аргументом с высоким приоритетом, а тест проверяет, где лежит файл |
| Часы браузера сбиты, живой таймер врёт | Поправка на расхождение по заголовку `Date` ответа сервера |
| Сервер остановлен, а страница открыта | Плашка «Нет связи с сервером» вместо потока ошибок и автоматическое переподключение |

## 13. Возможное развитие

1. Редактирование и удаление записей с журналом изменений.
2. Экспорт отчёта в CSV или Excel.
3. PostgreSQL и Testcontainers для многопользовательской работы.
4. Автоостановка забытых таймеров по расписанию.
5. Авторизация: сотрудник управляет только своим таймером, руководитель видит отчёты.
